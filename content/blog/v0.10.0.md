Kuberik 0.10 is out. When a build fails its bake, the rollout can now put the last good build back on its own and tell you exactly which failure made it do that.

<!--more-->

## Rolling back on its own

Turn on `autoRollback` for a rollout and a build that fails its bake no longer sits there waiting for someone to notice. The controller deploys the newest build that baked successfully, skipping gates so it goes out even during a schedule freeze, and the rollout page says what happened: which build failed, which build is running again, and each failure with whether it rolled back and why.

![A rollout that rolled back on its own — 2.4.0 failed its bake, 2.3.0 is running again, cart-smoke-test triggered it and cart-flaky-ui-test was opted out](/screenshots/blog/v0.10.0/rollback.png)

You decide which failures count. Each health check lists the kinds of failure that roll back, like a failed test, a workload that never got ready or a failed apply, and one annotation, `rollout.kuberik.com/rollback: "false"`, opts a single flaky test out. A version you pinned or force-deployed is never rolled back; it stays until you change it. [Roll Back Automatically](/docs/releases/rollback/) has the rules and their order.

Every rollout, with or without automatic rollback, now also remembers a build that failed there and doesn't pick it again. It stays held until someone deploys it by name, which in the dashboard is the Deploy anyway button next to it. History shows each rollback next to the deploy it undid.

![History — 2.4.0 failed and was rolled back automatically to 2.3.0, with the commit behind every deploy](/screenshots/blog/v0.10.0/rollback-history.png)

Canary tests got a fix that matters here. A test cancelled halfway by a pin or a rollback used to stay Failed and keep the next deploy stuck; openkruise-controller now clears it when the test goes back to waiting for its step.

## Health checks that say what failed

Knowing why matters just as much when nothing rolls back, so health checks now report what they saw, not just healthy or unhealthy. A Datadog monitor shows its value against the threshold, a Prometheus check lists every firing alert, and a Kustomization check names each resource that isn't ready. The figure is kept with the failed deploy, so it's still there after things recover.

![A failed deploy — payment errors at 3.1% over a 1% budget, with the Datadog monitors and the Prometheus alert that are failing](/screenshots/blog/v0.10.0/health.png)

The bake clock also stops while a check isn't healthy and starts again when it is, so a build can't bake through an outage. A check that can't run, because its provider is down or its credentials are wrong, now reads Pending instead of failing the build.

## Helm charts, natively

Until now kuberik reached a Helm chart through a Kustomization variable or the chart's OCI tag. Now it writes into the HelmRelease itself. Annotate it with `rollout.kuberik.com/values.image.tag.from: <rollout>` and the release goes into that value, or use `chart-version.from` when the chart version is what you release. A `helmrelease` health check waits until helm-controller has actually applied it, and the rollout page shows the chart, its version, the Helm revision and the pods it manages.

![A HelmRelease mid-upgrade — chart hello-helm 1.4.2, revision 8, with the new pods coming up next to the old ones](/screenshots/blog/v0.10.0/helm.png)

Writing into something Git also manages needs a clear rule, and Kustomization variables and OCIRepository tags now follow the same one as HelmReleases. The controller writes each rollout's value under that rollout's own field manager and no longer takes over a field another writer owns. If Git sets the same value, the deploy is refused with `HelmReleaseFieldConflict`, `KustomizationFieldConflict` or `OCIRepositoryFieldConflict` instead of the two quietly overwriting each other, and the banner on the rollout page names the reason, the field and the other writer. For Kustomizations and OCIRepositories that's a breaking change; see the upgrade notes below. The details are in [Flux CD](/docs/integrations/fluxcd/#set-a-helmrelease-value-or-chart-version).

## Approvals with a name on them

Approvals have their own API now. An `ApprovalPolicy` says which rollouts need one, and approving a build creates a `RolloutApproval` for that build as you, with your own Kubernetes permissions. From Kubernetes 1.30 an admission policy checks that the name on it is yours, so the history records who let it through.

In the dashboard that's an Approve button wherever a build waits for you, including Home. Home was rebuilt in this release to start with what needs a person: deploys that are failing, with the figure that's failing them, and builds waiting for your approval, next to your own changes and the rest of the fleet. The Environments and Apps pages were redone on the same design.

![Home — two failing deploys with their error rates and a Roll back button, a build waiting for approval in production, and the fleet beside them](/screenshots/blog/v0.10.0/home.png)

[Approvals](/docs/gates/approvals/) covers policies, who may approve, and moving gates you wrote by hand.

## Environments in order, regions in waves

Environments no longer point at each other. Their order comes from a fixed list of tiers, from development through test and staging to production, and one tier can span several clusters as sites. Sites roll out in waves. In each wave one site picks the release and the others deploy that exact pick, and the next wave starts once every site of the one before has baked it.

An app's new Progress tab draws where its newest release is across all of that.

![Progress of hello-waves-app — build c6f19d2 deployed through development and staging, then production in two waves across three regions](/screenshots/blog/v0.10.0/progress.png)

Releases come from a new place too. The release-controller, which the chart now installs, keeps the tags of the image a `ReleaseSource` names, in order, and every rollout takes its candidates from there instead of from a Flux `ImagePolicy`. If you already run an ImagePolicy, the ReleaseSource can point at it. [Sites and waves](/docs/concepts/environments/#sites-and-waves) and [Publish a release](/docs/releases/publish/) explain both.

## Upgrade

```bash {filename="upgrade.sh"}
helm repo update kuberik
helm upgrade kuberik kuberik/kuberik --namespace kuberik-system --version 0.10.0
```

Before you run it, check what Git sets of the version a rollout writes. Kuberik now writes the Kustomization's `postBuild.substitute` variable and the OCIRepository's `spec.ref.tag` under a field manager per rollout and no longer forces ownership, so if Git sets either, the next deploy is refused with `KustomizationFieldConflict` or `OCIRepositoryFieldConflict`. Remove the variable from the Kustomization, often a first value like `IMAGE_TAG: "1.0.0"` that earlier examples showed, and put the default in the manifest as `${IMAGE_TAG:=1.0.0}`. Remove `spec.ref.tag` from the OCIRepository. The same goes for a HelmRelease value a rollout writes. [Remove the Rollout's version fields from Git](/docs/installation/upgrade/#remove-the-rollouts-version-fields-from-git) walks through it.

The chart installs the new CRDs (`ApprovalPolicy`, `ClusterApprovalPolicy`, `RolloutApproval`, `ReleaseSource`, `ReleaseSlice`), the release-controller, the approval admission policies on Kubernetes 1.30 and later, and a new permission for the rollout-controller to patch Flux `helmreleases`. It moves every controller to the release that ships with chart 0.10.0, including the openkruise-controller with the canary-test fix.

After the upgrade, give every rollout a `ReleaseSource` and set `spec.releaseSourceRef`: `spec.releasesImagePolicy` is ignored now, and a rollout without a source deploys nothing new. Each Environment's `spec.environment` must now be a tier name, from `dev` through `staging` to `prod`: any other name closes its gate with `UnknownTier`, and two names of one tier used one after the other stop with `InvalidTopology`. `spec.relationship` is ignored, so remove it when convenient. Coming from chart 0.6.1 or earlier, hand the CRDs to the release first, as in [Install with Helm](/docs/installation/helm/#upgrade). Deploys made before the upgrade never roll back automatically; the first one after it can. [Upgrade Kuberik](/docs/installation/upgrade/) walks through all of it.
